# MetaStack 资料源评估

日期：2026-10-13

## 结论与实际访问范围

MetaStack 的公开文档描述了比当前已导入的 CS2.app 元数据更适合执行条件匹配的结构。建议优先核验少量完整战术，确认数据质量后接入。尚未导入实际战术，也未调用付费模型。

用户提供的 [Playbook](https://metastack.gg/Dlr2ZsuG/playbook) 初次访问要求登录。用户随后自行完成登录，现已读取三条完整战术页面和两条关联道具页面。尚未统计整个资料库的数量或完整率。

## 已确认的公开结构

- 战术支持地图、阵营、阶段/类型、说明、区域、职业队伍、视频、Demo 链接及 tick；角色可描述武器、站位或出生位依赖、职责、时间与协同，并关联道具。[Playbook 官方文档](https://help.metastack.gg/features/playbook.html)
- 道具支持类型、移动方式、投掷方式、投掷点与落点、练习位置和视角坐标、图片及视频。除基本字段外很多字段可不填写，不能假定每条完整。[Lineups 官方文档](https://help.metastack.gg/features/lineups.html)
- 官方的 Import 是导入 MetaStack 内的个人或团队空间；本次所读文档未确认站外导出或公开 API。[Import 官方文档](https://help.metastack.gg/metastack/import.html)

## 建议接入方式

1. 战术、角色、道具分开存储，以关联 ID 连接，保留原始链接、核验时间和缺失字段。
2. 先做执行条件检查，再检索排序：地图、阵营、回合阶段、存活人数、每人装备与现金、配合人数、站位和出生位要求。
3. 道具按角色分配，不能只看全队总量。同一人无法同时在两个投掷点完成同步任务；角色换人要重新验证位置和时序。
4. 买枪前检查能否购买所需装备；购买结束后按现有装备匹配。缺少关键道具时，优先换战术；只有来源明确支持的变体才可作为替代方案。
5. 大模型解释候选方案、人员任务及风险；确定性的装备与时序检查负责约束输出。未核验的数据保持未知，不能由模型补齐为事实。
6. 对手习惯仅来自推荐时点之前可获得的信息，并显示样本数量。不把检索相似度或职业案例胜率直接当作玩家采用该战术的胜率。

## 第一轮验证

登录后先核验 3–5 条完整战术及其关联道具，覆盖不同装备需求。记录来源是否给出逐人数量、必要/可选道具、步骤依赖及备用方案。

验证场景包括：装备满足、缺关键烟、缺支援闪、人数不足、总道具足够但角色无法同步执行、出生位不适合。预期系统能够分别解释可执行、不可执行或证据不足，而不是对所有场景给出同一套建议。

本阶段目标是可靠判断适配与可执行性；最高胜率需要另外建立可比样本及结果验证。

关键解析规则：

- 源角色名 `AWP Player` 不一定是该战术的武器硬要求。Nuke 强起条目的这个角色主要执行屋顶道具；不可仅由角色名推导必须购买 AWP。
- 同一道具链接在步骤中出现两次可能代表两次投掷。Nuke 屋顶角色明确有两颗闪，去重道具链接时不能同时去掉投掷次数。
- 回合钟为倒计时：1:46 在 1:40 之前。
- 描述未提及某角色使用道具，只能记为“没有描述到”，不能推断其真实完整库存为空。

已检查样本 JSON 可读取，角色数分别为 5、5、2，Nuke 描述道具计数与逐角色合计一致。这是结构化资料核验，不是战术效果验证。

## 当前交付边界与下一步

样本已落盘，但尚未并入现有网站检索索引；网站仍使用此前的 CS2.app 条目。下一步应先让检索支持角色级装备和步骤依赖，再用上述样本验证缺道具、缺协同、时机已过等场景。现有全队道具数量过滤不足以可靠处理这些战术，不应直接批量入库后宣布可执行。
